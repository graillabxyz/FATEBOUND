# OMNIPATH deployment

The product is OMNIPATH. `graillabxyz/FATEBOUND` is the requested legacy repository name. Existing local save keys, snapshot formats and native bundle identifiers remain stable to preserve compatibility.

## GitHub → Vercel → Supabase

- Vercel project: `omnipath`, scope `graillabxyzs-projects`.
- Git integration publishes `main` to production and branches/PRs to previews. GitHub Actions independently runs the engine tests, type checking and full web build.
- `npm run build:vercel` builds the public game, verifies that it contains no Dev Lab, then builds a separate developer metrics entry at `/metrics`. Data access is checked again on the server; hiding the dashboard is not the access boundary.
- `/api/*` executes `server/online/api.ts` on Vercel in Singapore. The API imports the same production content and match engine as the client. Backend and frontend therefore deploy from the same Git commit.
- Supabase project `mezepdrucimxsgkgikvp` stores identity, content, inventory, loadouts, private match authority, commands, sanitized per-player Realtime views, results, events and artwork.
- The Supabase `omnipath-api` Edge Function is a separately deployable diagnostic adapter of the same source. The Vercel website does not depend on that separately deployed copy. Rebuild it with `npm run build:edge` before an explicit Edge release.

## Environment configuration

`VITE_SUPABASE_URL` and `VITE_SUPABASE_PUBLISHABLE_KEY` are browser-safe. `VITE_ASSET_BASE_URL` points at the public `game-assets` bucket, with bundled artwork as the unconfigured/native fallback. `VITE_TELEMETRY_URL=/api/telemetry` enables authenticated usage transport.

`SUPABASE_URL` and `SUPABASE_SERVICE_ROLE_KEY` belong to Vercel server environments. The service-role key is sensitive and must never acquire a `VITE_` prefix, enter Git, or appear in logs. Preview deployments are connected to the same alpha database; use a Supabase branch/project before allowing untrusted preview code or production-scale changes.

Use local `.env.local` (ignored) for development. Schema changes are versioned under `supabase/migrations`; apply reviewed migrations explicitly. They are not run automatically by Vercel. `supabase/seed.sql` contains the current 104 gameplay definitions, generated by `npm run seed:catalog`. All are starter entitlements during this alpha.

## Authentication

`/account` supports Google OAuth and email/password. Configure Google's web client callback as:

`https://mezepdrucimxsgkgikvp.supabase.co/auth/v1/callback`

Put the Google Client ID and secret in Supabase's Google provider settings. Set Supabase's Site URL to the confirmed Vercel production origin and allow its `/account` redirect. Explicitly allow development and trusted preview `/account` URLs if needed. The initial developer allowlist is kept in the private schema. Membership is granted only after the exact email is confirmed; user-editable metadata cannot grant access.

The public game currently retains its local profile/economy and AI match UI. Cloud account, multiplayer transport and database authority are available; a player-facing room/matchmaking screen and server-backed progression/rewards remain follow-up product work. Local AI results are tagged client-reported; PvP results are authored by the server. Neither grants online currency or rank from client input.

## Multiplayer transport contract

Authenticated bearer tokens are verified against Supabase Auth on each request:

- `POST /api/matches/create` with `{loadout}` returns `{id, inviteCode}`. Loadouts must be owned and valid.
- `POST /api/matches/join` with `{inviteCode, loadout}` atomically fills seat 1 and initializes the real match engine. Invitation codes expire after one hour.
- `GET /api/matches/state?id=<uuid>` returns only the requesting participant's view. Nonparticipants receive 404. Server timeout processing runs on reads and commands; no client determines elapsed time.
- `POST /api/matches/command` with `{matchId, commandId, revision, plan}` validates actor, timing, dice costs, requirements and expected revision. Empty plans pass. UUID command IDs support retry deduplication. SQL compare-and-swap commits private state, projections, command receipt and final result atomically.
- Subscribe to `public.match_views` UPDATE events filtered by match ID. RLS delivers only the authenticated user's row. Full state, seed and command history never enter Realtime.

The transport uses invite rooms. Ranked matchmaking, disconnection grace/reconnection UX, scheduled idle-room cleanup, distributed abuse controls and production load testing are not implemented yet. The existing engine handles action/reaction timeouts when a participant polls; no background scheduler advances a match with both players offline.

## Verification

92 unit/integration tests pass, including the prior engine suite plus server actor/revision/timeout/privacy checks. A real disposable two-account Supabase run completed in four rounds with 18 commands, 16 Realtime updates, successful retry deduplication and persisted metrics. Cross-player projection reads and direct metrics/admin writes were rejected. QA accounts, match rows and results were removed afterward.

Four artwork objects were uploaded and their SHA-256 hashes stored in the manifest. Supabase security advisors reported no warnings/errors; informational no-policy notices are intentional default-deny tables accessed solely by the server. Native platform compilation and real Google consent cannot be verified without the configured provider and a user sign-in.
